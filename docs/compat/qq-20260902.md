# QQ Mail live observation — 2026-09-02

Scope: one owner-operated account on Windows, read-only commands plus local
index writes only. This record contains no addresses, subjects, folder
contents, message IDs, or authorization data.

## 1. Malformed BODYSTRUCTURE poisons the session (confirmed live)

- Reproduction: `sync` bulk-fetched envelopes with `BODYSTRUCTURE` among the
  FETCH items.
- Failure: go-imap v2.0.0-beta.8 aborted with
  `in response-data: in body-type-mpart: in body-type-1part: imapwire: expected SP, got "U"`.
  The wire decoder desynchronizes, so one message takes down the entire IMAP
  session. Reproducible on consecutive runs.
- Interpretation: at least one real message triggers a non-RFC-3501-compliant
  `BODYSTRUCTURE` response from imap.qq.com — consistent with the historical
  community report of QQ's malformed `UID FETCH` responses breaking JavaMail
  1.5.6. Raw server bytes were not captured (the decoder fails before any
  transcript point); a redacted raw fixture remains open for the S1-family
  raw-protocol probe.

## 2. Malformed ENVELOPE poisons the session too (confirmed live)

- After removing BODYSTRUCTURE from the fetch, the very next run failed with
  `in response-data: in envelope: imapwire: expected ')', got "1"` — the
  server-parsed ENVELOPE structure itself is malformed for at least one real
  message.
- Product decision (same day): bulk fetches trust the server only for
  numbers and flags (`UID`, `FLAGS`, `INTERNALDATE`, `RFC822.SIZE`). All
  structured text — subject, addresses, date — is fetched as raw header bytes
  via `BODY.PEEK[HEADER.FIELDS (...)]`, which travels in a length-prefixed
  literal that a noncompliant serializer cannot corrupt, and is parsed
  locally with charset-aware, lenient parsing. The guard test
  `TestBulkFetchNeverRequestsServerParsedStructure` keeps both ENVELOPE and
  BODYSTRUCTURE out of bulk fetches.
- Contract effect: `has_attachments` in bulk listings is now always `false`
  (the schema description says so); accurate detection is `attachment list`.

## 3. HEADER.FIELDS subsets return an empty body (confirmed live, probed)

- Symptom: every `BODY.PEEK[HEADER.FIELDS (...)]` fetch silently yielded no
  usable data against imap.qq.com. Field-level evidence: an index built by
  the affected code had `message_id` and `list_unsubscribe` empty for 100%
  of 8,464 rows — meaning header-fields fetches had never worked against the
  real server, while passing against the compliant in-memory CI server.
- Live probe (same account, same message, same connection semantics):
  - `BODY.PEEK[HEADER.FIELDS (FROM TO SUBJECT DATE)]` → section returned,
    **body length 2 bytes** (an empty header block).
  - `BODY.PEEK[HEADER]` → section returned, body length 4,547 bytes, fully
    parseable.
  So QQ does not honor HEADER.FIELDS filtering and signals nothing — it
  simply answers with an empty block. (An earlier hypothesis that the
  response section label failed to match the request was disproved by the
  same probe: the lookup matches fine.)
- Fix: all header fetches request the complete `BODY.PEEK[HEADER]` (a few KB
  per message) and pick fields locally; a source-level guard bans
  HEADER.FIELDS subsets from the client. `bodySectionBytes` is retained as a
  defensive single-section fallback. Verified live the same day: a
  from-scratch re-sync produced fully populated sender/subject/Message-ID
  and List-Unsubscribe fields.

## 4a. Per-message EXAMINE storms trip connection-rate limiting

- Reproduction: the clean gate verified a 2,823-message plan by doing, per
  message, one `EXAMINE` + one single-UID envelope fetch + one single-UID
  header fetch — roughly 8,500 round trips, almost all against one folder.
- Failure: `EXAMINE` began failing for a large, **drifting** fraction of
  messages — three consecutive full runs failed 1,797 / 1,491 / 1,545 of the
  2,823 with "folder examination failed", and the eligible count drifted too
  (987 / 1,282 / 1,231). Non-deterministic per-item SELECT failure under high
  request density is the signature of rate limiting, not a data problem.
- Fix: the gate now examines each folder once and batch-fetches all its
  envelopes and headers in 500-UID chunks — ~15 round trips instead of
  ~8,500. After the fix a full-plan read-only preflight produced a stable
  2,749 eligible with only deterministic, legitimate rejections and zero
  "folder examination failed". Follow-up worth doing: the execution phase
  still issues one SELECT per moved message; a selected-folder cache would
  remove that too.

## 4b. Manifest vs live Message-ID parser disagreement (2.3%)

- Observation: 65 of 2,823 messages (2.3%) were gated out as "server reports
  a Message-ID but the verified backup has none". Root cause is not the
  message: the backup manifest extracts Message-ID with `mimeparse.Parse`
  over the full raw .eml, while the gate extracts it with `net/mail` over
  `BODY.PEEK[HEADER]`. The two parsers disagree on a small tail of real-world
  headers.
- Decision: treat these as identity-uncertain and **leave them uncleaned**
  (the gate's conservative bias is correct — when identity match is in doubt,
  do not delete). Unifying the two extraction paths so the manifest and the
  gate agree is a worthwhile follow-up but not a blocker; the safe outcome is
  that a message the tool cannot positively re-identify stays in the mailbox.

## 4d. IMAP MOVE is not transactional: a dropped response reports a false failure

- Observation: a clean execution of 2,749 messages reported "2748/2749; 1
  failed: unexpected internal error". An independent read-only verification
  immediately afterward found all 2,749 gone from their source folders
  (already_gone=2749, eligible=0). The one "failed" move had in fact
  succeeded server-side; the client hit QQ's intermittent `unexpected EOF`
  while reading the command completion and reported an error.
- Consequence: the CLI's reported success count can undercount the true
  result — a `UID MOVE` executed by the server but not acknowledged to the
  client looks like a failure. It never overcounts (a message the server did
  not move stays in place), so the direction of error is safe.
- Mitigations already in place: reruns are safe (moved messages are
  already_gone and skipped), and the local backup covers everything.
  Follow-up worth doing: after execution, a read-only reconciliation pass
  could backfill the true moved-count and downgrade dropped-response
  "failures" to confirmed moves.

## 4c. Long sync sessions can be cut mid-run (`unexpected EOF`)

- During from-scratch syncs of a mailbox with thousands of messages, the
  connection was occasionally closed mid-batch (`unexpected EOF`), roughly
  after tens of seconds of continuous FETCH traffic. Not conclusively
  attributed (server-side limit vs. network); no rate-limit response was
  observed.
- Mitigation already in place: ascending 500-message batches commit the UID
  watermark per batch, so an interrupted `sync` resumes where it stopped —
  rerunning converges. Callers should treat a failed first sync as resumable
  rather than fatal.

## Verification after the fixes

- A from-scratch `sync` over all five selectable default folders completed
  on the real account (with resume across interrupted attempts), and
  spot-checked rows carried populated from/subject/Message-ID and
  List-Unsubscribe fields.
